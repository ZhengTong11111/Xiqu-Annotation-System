# 数据盘迁移与未来恢复快照策略执行计划

> 这是一份明天可以直接照着执行的生产运维任务单。它把 PostgreSQL 迁移到数据盘和未来
> `reconstructible` 恢复快照策略分成有明确门禁的阶段。除非上一阶段的验收证据完整，否则不要继续下一阶段。
>
> 本文不是开发计划，也不是把本机数据库复制到生产的脚本。所有生产命令都必须在服务器上根据现场实际路径复核后执行。
> 通用 release、维护模式、备份、systemd、Caddy 和跨服务器恢复规则以
> [`server-deployment.md`](./server-deployment.md) 为准；恢复快照专项合同以
> [`annotation-history-server-migration.md`](./annotation-history-server-migration.md) 为准。

## 一、明天的目标和边界

### 目标

1. 在不改变任何业务数据内容的前提下，把 PostgreSQL 数据目录迁移到 `/var/lib/xiqu-platform` 数据盘。
2. 让 PostgreSQL、API、analysis worker 在数据盘挂载缺失时 fail closed，不能悄悄写入系统盘上的空目录。
3. 在数据库位于数据盘且运行稳定后，再上线第 40、41 条 expand-only migration。
4. 先保持未来快照 rollout 关闭，验证已有 `inline` 历史、保存、协作和恢复功能。
5. 获得独立授权后，才短时间启用 `future-reconstructible-v1`，只验证未来新保存，不改造旧历史。

### 绝对不能做的事

- 不能复制本机 `.env`、本机 PostgreSQL、开发 seed 或本机对象目录到生产。
- 不能删除、置空、压缩、归档或重写已有恢复快照、标注文件、operation、确认、评论、反馈、审核链接或媒体对象。
- 不能运行 `db push`、`db push --force-reset`，不能手工改 `_prisma_migrations`，不能删除 migration 记录。
- 不能为了释放空间运行 `VACUUM FULL`、`pg_repack`、compactor、payload 清理或 shadow recipe apply。
- 不能在没有确认数据盘挂载成功的情况下启动 PostgreSQL。
- 不能把第 40、41 条 migration 和开启 rollout 当作一个不可拆分的动作。
- 不能把密码、`DATABASE_URL`、AccessKey、Web License、PlayAuth、临时媒体 URL、完整环境文件或 ProjectData 写入记录。

## 三、总门禁：空间、备份和在线用户

### 1. 空间门禁

迁移至少会产生一份 PostgreSQL 数据目录副本。若需要新建一致备份，还要计算数据库 dump、对象备份和 manifest 的峰值空间。
不要只看“复制前够用”，要计算复制和备份同时存在时的最低余量。

```bash
df -h / /var/lib/xiqu-platform
sudo du -xsh /var/lib/postgresql/16/main /var/lib/xiqu-platform/storage \
  /var/lib/xiqu-platform/backups /var/lib/xiqu-platform/builds 2>/dev/null
sudo -u postgres psql -d postgres -Atc \
  "SELECT pg_size_pretty(pg_database_size(current_database()));"
```

继续执行必须同时满足：

- 数据盘可用空间至少覆盖 PostgreSQL 实际大小、必要备份临时空间，并在所有步骤结束后仍保留明确的生产安全余量。
- 迁移过程中系统盘即使保留旧目录作为回滚副本，也不能跌破已批准的系统盘安全余量。
- 不能用删除业务数据、快照 payload、operation、媒体或当前正式备份来制造余量。
- 不确定备份峰值时，优先使用已验证且存放在独立位置的最近一致备份；不要在数据盘上盲目再复制一份大型完整备份。

这里的“安全余量”必须根据明天实际磁盘、备份大小和运维经验填写到变更记录中。任何低于门槛的结果都意味着停止，
不是继续执行后再想办法清理。

### 2. 备份门禁

迁移 PostgreSQL 数据目录前，必须拥有可验证的一致恢复基线。最近已有通过校验的备份且覆盖当前数据库与整个对象存储时，
可以复用该备份，但要重新确认它的时间、manifest、checksum 和存放位置；否则在维护窗口中创建新的完整备份。

一致备份必须满足：维护模式已经开启、API 写入已排空、analysis worker 已停止。备份校验失败时保持维护和 worker 停止，
不得继续迁移。

```bash
# 以下命令应从旧的稳定 release 执行；具体备份 id 和路径只记录在受控运维记录中。
sudo -u xiqu bash -c '
  set -a
  source /etc/xiqu-platform/xiqu-platform.env
  set +a
  cd /opt/xiqu/current
  npm run maintenance:enable -- \
    --operator platform.admin \
    --reason "PostgreSQL 数据盘迁移与恢复快照策略准备"
'

sudo systemctl stop xiqu-analysis-worker
sudo systemctl is-active xiqu-analysis-worker  # 必须为 inactive

sudo -u xiqu bash -c '
  set -a
  source /etc/xiqu-platform/xiqu-platform.env
  set +a
  cd /opt/xiqu/current
  npm run backup:create -- \
    --operator platform.admin \
    --output /var/lib/xiqu-platform/backups \
    --reason "PostgreSQL 数据盘迁移前一致备份" \
    --require-existing-maintenance
'

sudo -u xiqu bash -c '
  cd /opt/xiqu/current
  npm run backup:verify -- \
    --backup /var/lib/xiqu-platform/backups/xiqu-backup-<实际备份目录>
'
```

不要把完整备份输出、数据库 dump、对象内容或环境文件提交到 Git。记录只保留备份 id、对象数量、字节数、manifest/checksum
结果和报告路径。

### 3. 在线用户门禁

- 通知当前标注者在窗口前保存并暂时停止编辑。
- 确认关键会话显示“已同步”，没有进行中的恢复、上传、分析或结构租约事务。
- 维护模式启用后，确认新写入被拒绝或排空，而不是继续排队等待数据库迁移。
- 记录活动处理任务的聚合数量；不要导出任务正文、凭据或媒体临时 URL。

## 四、第一阶段：把 PostgreSQL 接管到数据盘

这一阶段只改变 PostgreSQL 的物理数据目录位置，不改变 schema、API 业务逻辑或快照存储形态。建议使用“在线预复制 +
短维护窗口最终同步”，把停机时间压缩到最后一次 rsync 和服务验证。

### 1. 只读确认 PostgreSQL 服务和目录

```bash
sudo systemctl list-units --type=service 'postgresql*' --no-pager
sudo -u postgres psql -d postgres -Atc "SHOW data_directory; SHOW config_file;"
sudo du -sh /var/lib/postgresql/16/main
sudo findmnt -T /var/lib/postgresql/16/main
```

如果实际集群名称不是 `16-main`，后文的 systemd 单元和路径必须全部替换成现场值，不得照抄。

### 2. 在数据库继续运行时预复制

目标目录必须位于已经确认的独立数据盘，并且是新建的空目录。不要用系统盘作为中转目录。

```bash
sudo install -d -o postgres -g postgres -m 700 \
  /var/lib/xiqu-platform/postgresql/16/main

sudo rsync -aHAX --numeric-ids --info=progress2 \
  /var/lib/postgresql/16/main/ \
  /var/lib/xiqu-platform/postgresql/16/main/

sudo du -sh /var/lib/postgresql/16/main \
  /var/lib/xiqu-platform/postgresql/16/main
```

预复制完成后不要删除旧目录。预复制只能减少停机时间，不是数据库一致备份；最后同步必须在 PostgreSQL 停止后完成。

### 3. 短维护窗口内完成最终同步

在这一小段窗口中，维护模式和 worker 必须已经处于正确状态。先停止 API，避免 API 在 PostgreSQL 切换过程中不断重试；
然后停止 PostgreSQL。服务名必须用前面现场检查到的实际单元。

```bash
sudo systemctl stop xiqu-api
sudo systemctl stop postgresql
sudo systemctl is-active postgresql  # 必须为 inactive

sudo rsync -aHAX --numeric-ids --delete --info=progress2 \
  /var/lib/postgresql/16/main/ \
  /var/lib/xiqu-platform/postgresql/16/main/

sudo chown -R postgres:postgres /var/lib/xiqu-platform/postgresql/16/main
sudo chmod 700 /var/lib/xiqu-platform/postgresql/16/main
```

`--delete` 只能用于前面明确创建、没有其他业务内容的目标目录；如果目标目录不是本次新建的空目录，立即停止。

### 4. 建立持久且有启动门禁的挂载

推荐用 bind mount 保留原路径，让 Debian/Ubuntu 的 PostgreSQL cluster 配置不需要改写大量路径。先把旧目录改名保存，
再把目标目录挂到 PostgreSQL 原路径。旧目录在观察期内不得删除。

```bash
STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
sudo mv /var/lib/postgresql/16/main \
  "/var/lib/postgresql/16/main.pre-data-disk-${STAMP}"
sudo install -d -o postgres -g postgres -m 700 /var/lib/postgresql/16/main

sudo mount --bind \
  /var/lib/xiqu-platform/postgresql/16/main \
  /var/lib/postgresql/16/main

findmnt -T /var/lib/postgresql/16/main
df -h / /var/lib/xiqu-platform
```

把 bind mount 写入 `/etc/fstab` 前先检查是否已有同一路径记录。建议使用明确的 mount 依赖，避免数据盘未挂载时
PostgreSQL 只看到一个空的普通目录：

```text
/var/lib/xiqu-platform/postgresql/16/main /var/lib/postgresql/16/main none bind 0 0
```

写入后执行：

```bash
sudo systemctl daemon-reload
sudo mount -a
findmnt -T /var/lib/postgresql/16/main
```

同时检查 PostgreSQL systemd 单元是否明确依赖数据盘：

```bash
sudo systemctl cat postgresql
sudo systemctl cat postgresql@16-main
```

如果现场单元没有可靠的挂载依赖，应创建受控 systemd drop-in，加入 `RequiresMountsFor=/var/lib/xiqu-platform`，然后执行
`daemon-reload`。drop-in 的实际单元名必须以现场结果为准。启动前必须人工确认 `findmnt` 成功；不能用 `nofail` 让数据库在
数据盘失败时照常启动。

### 5. 启动并验证数据库

```bash
sudo systemctl start postgresql
sudo systemctl is-active postgresql
sudo -u postgres psql -d postgres -Atc "SHOW data_directory;"
sudo -u postgres psql -d postgres -Atc \
  "SELECT pg_size_pretty(pg_database_size(current_database()));"
```

必须同时确认：

- PostgreSQL active，`SHOW data_directory` 仍显示原逻辑路径，但该路径通过 `findmnt` 实际落在数据盘。
- 数据库能够读取当前业务 schema、表和索引，数据库大小与迁移前在合理误差内。
- PostgreSQL 日志没有启动恢复、checksum、权限、表空间或 I/O 错误。
- `/var/lib/postgresql/16/main.pre-data-disk-*` 仍存在，大小和原目录相符。

此时可以先启动旧 API 做只读 readiness smoke，但仍保持维护模式：

```bash
sudo systemctl start xiqu-api
sudo systemctl is-active xiqu-api
curl -fsS http://127.0.0.1:4317/api/health/live
curl -fsS http://127.0.0.1:4317/api/health/ready
```

如果数据库启动失败、数据盘挂载不正确、数据库摘要不一致或 readiness 失败，进入第八节回滚，不执行 migration。

## 五、第二阶段：部署 40/41 migration，但保持 rollout 关闭

数据目录迁移成功后，先观察 PostgreSQL 和旧 release 30--60 分钟。观察期间不切换未来快照策略；确认数据库稳定后再安排
第二个尽量短的维护窗口。若明天需要连续完成，也必须保留“数据盘验证通过”这一逻辑停顿，不能把两次风险混成一步。

### 1. 组装候选 release

候选 release 必须来自已经审查并提交的同一 commit，包含与 Prisma Client 匹配的第 40、41 条 migration、编译后的
`packages/shared` 和 `packages/document-model`。不能直接把当前工作树或本机 `node_modules` 临时上传到生产。

在本机完成：

```bash
npm run build
npm run release:inspect -- --release-dir <候选 release 目录>
npm run release:check -- --release-dir <候选 release 目录>
```

候选门禁必须确认 migration 数量为 41，且最后两条实际名称与仓库目录一致。不要使用旧的、混入已删除 migration 的候选目录。

### 2. 第二个维护窗口的执行顺序

1. 读取并记录当前 release 的真实绝对路径，作为 `release:switch --expected-current`。
2. 启用维护模式，等待写入排空，停止 analysis worker。
3. 再次确认 PostgreSQL 数据盘挂载、空间余量和 rollout 仍为 `disabled`。
4. 从新候选 release 执行 `npm run db:deploy`，禁止 `db push`。
5. 检查 migration 从 39 变为 41，`prisma migrate status` 为 up to date。
6. 使用 `release:switch` 原子切换 API release，重启 API，维护状态下执行 readiness 和只读 smoke。
7. 先保持 rollout=`disabled`，只验证旧 inline 历史和新代码读取路径。
8. 低干扰解除维护并启动 analysis worker，执行一次受控保存与协作追赶验收。

执行 migration 的命令形态：

```bash
NEW_RELEASE=/opt/xiqu/releases/<经过门禁的候选 release>

sudo -u xiqu env NEW_RELEASE="$NEW_RELEASE" bash -c '
  set -a
  source /etc/xiqu-platform/xiqu-platform.env
  set +a
  cd "$NEW_RELEASE"
  npm run db:deploy
'

sudo -u xiqu env NEW_RELEASE="$NEW_RELEASE" bash -c '
  set -a
  source /etc/xiqu-platform/xiqu-platform.env
  set +a
  cd "$NEW_RELEASE"
  npx prisma migrate status
'
```

若 migration 中途失败，保持维护和 worker 停止，先看数据库事务状态、migration 日志和服务日志；不能手工删除 migration
记录，也不能立刻反复执行。第 40、41 条必须是 expand-only，不能更新或删除已有快照行。

## 六、rollout 关闭阶段的验收

这一阶段的目的，是证明数据库位置变化和 schema 扩展没有影响已有生产功能。环境键必须保持：

```text
XIQU_ANNOTATION_HISTORY_FUTURE_SNAPSHOT_ROLLOUT=disabled
```

### 必须验收的旧数据

- 打开包含长期历史的标注文件，恢复历史列表可以分页加载。
- 打开历史详情、比较和恢复入口，旧 `inline` payload 能正常读取。
- 检查带确认、评论、反馈、审核链接和媒体绑定的文件，这些事实数量和内容没有减少。
- 检查最近的 revision、operation、协作 catch-up 和保存状态，revision 连续递增。

### 必须验收的新行为

- 普通文字、时间、结构编辑可以保存，返回资源管理器前会等待服务器保存和本地 draft 清理完成。
- 两个账号先后编辑和同时编辑时，冲突协调、后到编辑结果和错误日志仍正常。
- analysis worker active，已有波形、频谱和 F0 读取正常；不在本阶段运行历史 compactor。
- `/metrics`、系统诊断、审计和 recovery history 请求没有新的 5xx 或未处理异常。

验收通过后，才可以关闭维护。若验收失败，保持维护，优先只回滚 API release；数据库仍保持 41 条 migration，不手工逆向。

## 七、第三阶段：单独启用 future-reconstructible-v1

这不是数据库迁移的附带步骤。只有第二阶段观察和人工验收全部通过，并且有单独授权，才执行。

### 1. 开启前检查

- 第 40、41 条 migration 已完成，Prisma schema 能力检查通过。
- 旧 `inline` 快照、恢复、比较、协作、确认、评论、反馈和审核链接已经验收。
- 数据盘仍有足够余量；没有正在进行的恢复、批量导入、迁移或异常保存重试。
- 已准备一个低风险、可人工核验的测试标注文件；不要用唯一生产材料做 canary。
- 已确认新 release 的 resolver、writer、保存事务和指标来自同一 commit。

### 2. 只改一个环境键

在服务器编辑环境文件时，只改变 rollout 键，保留其他键、权限和换行格式：

```bash
sudoedit /etc/xiqu-platform/xiqu-platform.env
# 只将对应配置改为：
# XIQU_ANNOTATION_HISTORY_FUTURE_SNAPSHOT_ROLLOUT='future-reconstructible-v1'

sudo chmod 640 /etc/xiqu-platform/xiqu-platform.env
sudo systemctl restart xiqu-api
sudo systemctl is-active xiqu-api
curl -fsS http://127.0.0.1:4317/api/health/ready
```

启动后先看 readiness、日志和 metrics。不要在前端连续点击保存来“试出结果”，每次 canary 操作都要记录时间和文件标识。

### 3. 受控 canary

在测试文件中完成一次普通、可重放的编辑保存，确认界面显示已同步，然后打开恢复历史并读取刚产生的记录。后台只读检查
只输出计数和轻量状态，不输出 payload：

```bash
sudo -u xiqu bash -c '
  set -a
  source /etc/xiqu-platform/xiqu-platform.env
  set +a
  psql "$DATABASE_URL" -Atc "
    SELECT storage_mode, COUNT(*)
    FROM annotation_recovery_snapshots
    GROUP BY storage_mode
    ORDER BY storage_mode;
  "
'
```

每一条 `reconstructible` 行都必须满足下列事实完整，不能只看 `storage_mode`：

```text
payload IS NULL
compacted_at IS NOT NULL
checkpoint_snapshot_id IS NOT NULL
operation_revision_start IS NOT NULL
operation_revision_end IS NOT NULL
operation_sequence_start IS NOT NULL
operation_sequence_end IS NOT NULL
operation_count IS NOT NULL
payload_sha256 IS NOT NULL
recipe_verified_at IS NOT NULL
```

同时检查：

- 旧 `inline` 行数量没有下降，旧 payload 没有被置空。
- 新记录详情、比较、恢复可以通过 resolver 得到与保存时一致的 ProjectData。
- 产生的快照与 operation、checkpoint 在同一 revision 事实链上，没有孤立 recipe。
- 普通保存、原子命令保存、恢复前保护和协作 catch-up 没有出现 5xx、同步失败或 stale claim。
- `schema_not_ready` 回退计数为 0；若非 0，说明 rollout/schema 顺序有问题，应修复而不是重复保存。

如果无法确认 canary 结果，立即把 rollout 改回 `disabled`，重启 API，保留新行和日志，不要手工删除或修改新快照。

### 4. 关于回滚的特别限制

- 在 rollout 关闭且没有产生 `reconstructible` 行前，39 条旧 release 对 40/41 条 expand-only schema 的代码回滚通常可行，
  但仍需在维护和 worker 停止状态下使用 `release:switch` 验证。
- 一旦已经产生任何 `reconstructible` 行，不能把旧的只认识完整 inline payload 的 release 当作无条件回滚目标。
  优先将 rollout 关回 `disabled`，继续使用支持 resolver 的候选 release。
- 如果支持 resolver 的 release 也无法稳定读取，必须保持维护和 worker 停止，使用已验证的一致备份按正式恢复/接管流程同时
  恢复数据库和对象，而不是只回滚代码或清空 recipe。

## 八、失败处理和 PostgreSQL 数据盘回滚

### A. 数据盘迁移尚未启动 PostgreSQL

如果最终 rsync 失败或新目录 checksum/大小不合理：

1. 保持 API 停止、维护开启、worker 停止。
2. 不删除旧目录，不启动指向不明的 PostgreSQL。
3. 卸载 bind mount（若已挂载），删除本次新建的空 mountpoint。
4. 恢复旧目录原名，执行 PostgreSQL 启动和只读检查。

### B. 新数据目录 PostgreSQL 启动失败

```bash
sudo systemctl stop postgresql
sudo umount /var/lib/postgresql/16/main
sudo rm -rf /var/lib/postgresql/16/main  # 仅限确认它是本次新建的空 mountpoint
sudo mv /var/lib/postgresql/16/main.pre-data-disk-<时间戳> \
  /var/lib/postgresql/16/main
sudo systemctl start postgresql
sudo -u postgres psql -d postgres -Atc "SHOW data_directory;"
```

如果 `rm -rf` 的目标不是本次新建的空 mountpoint，禁止执行，改为人工核对。修正 `/etc/fstab` 和 systemd drop-in 后，
执行 `daemon-reload`，确认数据库确实回到旧目录，再启动 API。

### C. migration 或新快照策略失败

- rollout 失败但数据库和 resolver 可读：改回 `disabled`，重启 API，保留现场，继续只读观察。
- migration 失败且没有不确定写入：保持维护，确认事务结束后按 release 手册回滚代码。
- 出现数据库/对象不确定写入、恢复 hash 不一致或历史事实缺失：不能只回滚代码，使用同一份已验证一致备份恢复数据库和对象。
- 任何回滚都不能删除 `_prisma_migrations`、快照行、operation 或治理事实。
